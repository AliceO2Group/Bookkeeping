Bookkeeping HTTP API

HTTP API of the ALICE Bookkeeping. Internal use only.

Work in progress: not every resource is documented yet. Only the sections listed below exist.

Authentication

Every request carries a JWT in the token query parameter (e.g. GET /api/tags?token=<jwt>). The token's access claim lists the user's roles; operations marked with a role below return 403 otherwise.

Response envelope

Successful responses are { "data": ... }, with meta.page added on paginated endpoints. Failed responses are { "errors": [ { status, title, detail?, source? } ] }. Note that request-validation failures are sent with HTTP 400 while each error's status field says "422".

Conventions

  • Filters use bracket syntax: filter[partialText]=foo. List-valued filters are comma separated: filter[ids]=1,2,3.
  • Pagination uses page[limit] and page[offset].
  • Timestamps are Unix epoch milliseconds.
  • Operations flagged x-llm-exclude: true change data and are not meant for LLMs or MCP tools; skip them when generating tools.

Instructions for LLMs and automated agents

  • Always paginate when an endpoint supports page[limit] and page[offset]. Never rely on the default: when page[limit] is omitted the server may return up to 5000 items, which is far too much for a model context.
  • Request at most 100 items per call (page[limit]=100). This is a rule for LLMs and agents, not a server limit (the server accepts more).
  • To read more, repeat the call increasing page[offset] by the limit until offset reaches meta.page.totalCount.
  • Prefer narrowing the request with filter[...] parameters over reading everything and filtering afterwards.
  • Endpoints that are not paginated (for example GET /tags) return everything: use their filters.
  • Do not call operations flagged x-llm-exclude: true: they create, change or delete data.

Quick start

The examples below read the server address and the JWT from the environment:

export BOOKKEEPING_URL=http://localhost:4000
export TOKEN=<your jwt>

curl -g is needed because of the [ ] in filter names. Note that a token in the URL ends up in shell history and server logs.

Tags

Labels attached to logs (and runs). Each tag may notify an e-mail list and a Mattermost channel.

GET /tags - List tags

Operation id: listTags

Returns every tag matching the filters, not paginated. Returns 204 No Content (empty body) when nothing matches, so clients must not assume a JSON body.

Parameter In Type Required Notes
filter[ids] query string no Comma separated tag ids.
filter[texts] query string no Comma separated exact tag texts. Takes precedence over filter[partialText].
filter[partialText] query string no Substring match on the tag text. Ignored when filter[texts] is given.
filter[emails] query string no Comma separated e-mail addresses.
filter[mattermosts] query string no Comma separated Mattermost channel names.

Responses:

  • 200: Matching tags.
  • 204: No tag matches the filters. No body.
  • 400: The request failed validation. HTTP status is 400 although each error's status field is "422". source.pointer has the form /data/attributes/<query|params|body>/<field>.
curl -g "$BOOKKEEPING_URL/api/tags?token=$TOKEN"

POST /tags - Create a tag not for LLM use

Not meant for LLM or MCP tool use (x-llm-exclude).

Required role: admin

Request body (JSON):

Field Type Required Notes
text string yes Words, digits, - and + only. min length 2, max length 20, pattern [\w|\-+]{1,}
description string | null no max length 100
mattermost string | null no
email string | null no One or more e-mail addresses, comma separated.
color string | null no pattern ^#[0-9A-Fa-f]{6}$

Responses:

  • 201: The created tag.
  • 400: The request failed validation. HTTP status is 400 although each error's status field is "422". source.pointer has the form /data/attributes/<query|params|body>/<field>.
  • 403: The token lacks the role required by this operation.
  • 409: A tag with the same text already exists.
curl -g -X POST "$BOOKKEEPING_URL/api/tags?token=$TOKEN" \
  -H 'content-type: application/json' \
  -d '{"text":"FOOD","description":"Food related issues","email":"cake@cern.ch,test@cern.ch","mattermost":"food-channel","color":"#ff8800"}'

Shifts

Data used to fill end-of-shift reports.

GET /shift-data - Get the data of the pending shift of the calling user

Operation id: getShiftData

Returns what a shifter needs to write their end-of-shift (EoS) report for the pending shift: the current shift, or the previous one during the 30 minutes that follow its end. Shifts last 8 hours and are Night (23h-7h), Morning (7h-15h) and Afternoon (15h-23h) in the Geneva time zone. The shift is deduced from the current time and the calling user, not from a parameter.

typeSpecific depends on shiftType: { environments } for ECS, { runs } for QC/PDP, { runs, tagsCounters } for SL, and null for SLIMOS and DCS.

Parameter In Type Required Notes
shiftType query string yes Kind of shift.

Responses:

  • 200: The shift data.
  • 400: The request failed validation. HTTP status is 400 although each error's status field is "422". source.pointer has the form /data/attributes/<query|params|body>/<field>.
  • 404: The calling user is not known to Bookkeeping.
curl -g "$BOOKKEEPING_URL/api/shift-data?shiftType=ECS&token=$TOKEN"

POST /gaqDetectors - Set the detectors contributing to the GAQ of runs in a data pass not for LLM use

Operation id: setGaqDetectors

Requires the role admin or gaq. For each given run, replaces the detectors contributing to the GAQ in the data pass by the given ones. Every run must be linked to the data pass and have every given detector.

Not meant for LLM or MCP tool use (x-llm-exclude).

Required role: admin, gaq

Request body (JSON):

Field Type Required Notes
dataPassId integer yes
runNumbers array yes Run numbers of the runs to update, without duplicates.
detectorIds array yes Ids of the detectors contributing to the GAQ, without duplicates.

Responses:

  • 201: The created associations between runs and detectors, one per run and detector.
  • 400: The request failed validation (see the validation errors format), or a run is not linked to the data pass, a detector does not exist or a run does not have a given detector. In these last cases the error has title: Service unavailable and the reason in detail.
  • 403: The token lacks the role required by this operation.
  • 404: The data pass does not exist.
curl -g -X POST "$BOOKKEEPING_URL/api/gaqDetectors?token=$TOKEN" \
  -H 'content-type: application/json' \
  -d '{"dataPassId":3,"runNumbers":[49,56],"detectorIds":[4,7]}'
